# 日志系统

> 本文档说明两端**实际会输出什么日志、日志放在哪、怎么读、怎么看**。
> Android 与 iOS 各有独立的落盘位置与命名，但日志的**语义与关键字体系是同一套**
> （共享源码 `jni/*` 输出的行在两端完全一致）。

- Android 侧细节：[README 第十节](../README.md#十日志与排查)
- iOS 侧细节：[iOS/README 第七节](../iOS/README.md#七日志与排查)

---

## 一、输出通道

| | Android | iOS |
|---|---|---|
| 系统日志 | `logcat`，tag = `settingsframework`，级别 INFO | `os_log`，子系统 `com.scode.lztsettingsframework` |
| 文件日志 | `/sdcard/Android/data/<包名>/files/settingsframework.log` | `<沙盒>/Documents/lztsettingsframework.log` |
| 崩溃日志 | 与文件日志同文件（`NATIVE_CRASH` 行） | 独立文件 `<沙盒>/Documents/lztsettingsframework_crash.log`（追加写） |

三处**内容完全相同**——同一行日志会同时进系统日志和文件日志；区别只在
「崩溃现场是否单独落盘」。

> **文件名注意**：Android 叫 `settingsframework.log`（与 `.so` 同名），
> iOS 叫 `lztsettingsframework.log`（与 dylib 同名）。两端命名各自与自身
> 产物一致，**跨端对照时不要按同一个名字去找**。

## 二、文件日志的生命周期

两端采用同一套策略：

1. **每次启动清空重建**：当前日志以 `"w"` 模式打开，因此**它只包含最近
   一次启动**的输出。
2. **上一份自动归档**：启动时把上一份改名为
   `<主名>-<yyyyMMdd-HHmmss>.log`（文件名字典序即时间序）。
3. **只保留最近 5 份**：更早的归档自动删除。
4. **首行是 BOOT 行**：`===== BOOT <本地时间戳> =====`，便于把日志与操作时间对齐。

这样「要发哪份日志」永远只有一个答案：**当前这个固定名**。
若问题发生在更早的一次启动，按时间戳在同目录找对应归档。

Android 的文件头还会额外打印包名、日志路径与 CPU 架构：

```text
===== BOOT 2026-11-21 23:41:07.512 =====
=== settingsframework Log ===
package: com.example.game
log path: /sdcard/Android/data/<pkg>/files/settingsframework.log
arch: arm64-v8a
```

## 三、日志种类

日志行按前缀分类。下面是当前代码里**实际会输出**的类别。

### 3.1 启动与装载（两端共有）

| 关键字 | 含义 |
|---|---|
| `===== BOOT ... =====` | 本次启动的起点 |
| `applyHooks: base = 0x...`（Android） | 定位到主库基址并开始安装 hook |
| `main __TEXT base = 0x...`（iOS） | 定位到主程序基址 |
| `libPVZ2.so loaded after %dms`（Android） | 主库加载完成 |
| `=== lzt iOS main module start/ready ===`（iOS） | iOS 模块启动与就绪 |
| `BUILD v2.1.0-SETTINGS-FRAMEWORK mode=... debug=...`（Android） | 构建模式（Release / Debug） |

### 3.2 设置框架 `[SFW]`

前缀 `[SFW]` 覆盖整个框架层的生命周期：

```text
[SFW] module registered: anchor=6 slot=1 reqTab=0
[SFW] tab id finalized: 30 (anchor=6 slot=1)
[SFW] createTab: insert slot=1 tabId=30 -> 语言
[SFW] dispatch: widget click id=33 page=0x...
[SFW] dirty rebuild: page=0x... module=1
[SFW] engine install: create=1 dispatch=1 page=1 modules=2
```

覆盖的环节：模块注册 → id 分配 → Tab 注入 → 页面物化 → 控件点击 →
dirty 重建 → 本地化回填。

### 3.3 语言与本地化

| 关键字 | 含义 |
|---|---|
| `LangTable: source=... languages=N enabled=M` | 语言表来源命中结果 |
| `Language startup: source=flag locale=...` | 启动期读到了语言标识文件 |
| `Language startup: flag missing or invalid` | 无标识文件，转入配置分支 |
| `Language startup: config ready=1 waitMs=N` | 等到配置对象可读 |
| `Language startup: source=game-config locale=...` | 用配置里的语言 |
| `Language switch: target=0x........ locale=...` | 准备切换到目标语言 |
| `Language config save: radio prev=... next=...` | 用户选择的写入 |
| `Language config save: readback next=N` | 写入后回读校验 |
| `Lang hot_reload: begin/end locale=... table=...` | 热重载流程边界 |
| `LangOverride: ...` | 启动期语言标识的三条判定分支 |
| `LawnStrings: loaded N entries (locale, source=...)` | 语言表实际载入结果 |
| `[LZ] refresh_all: captured=N refreshed=M` | 已显示文本的即时回填 |

**Android 与 iOS 的启动期语义不同**（这是两端最重要的一处差异）：

- Android：启动期读到配置后**当场写标识 + 接管**，立即生效。
- iOS：启动期**只记录不干预**，把切换推迟到主界面（详见 3.4）。

因此 iOS 日志里会出现这一行，Android 不会出现：

```text
Language startup: source=game-config locale=zh-cn [deferred to main-screen rule2]
```

### 3.4 iOS 语言三条规则

iOS 的启动期语言判定分三条规则，日志里可直接看出走了哪条：

| 规则 | 条件 | 行为 | 日志 |
|---|---|---|---|
| ① | 标识文件存在 | 与游戏当前值比对，相同放行 / 不同用文件里的值 | `LangOverride: flag -> locale=... fourcc=0x...` |
| ② | 无标识文件、有配置 | 主界面后完整换表 + 写标识 | `LangOverride: rule2 config locale=... -> 0x...` |
| ③ | 无标识文件、无配置 | 全程不干预 | `LangOverride: rule3 no config, pass through (langs=N ready=N)` |

### 3.5 视角模块

| 关键字 | 含义 |
|---|---|
| `H0 BoardZoom2: scale ... -> 1.0`（Android） | 高视角下强制缩放比 |
| `H1 BoardZoom pre/post` | 布局缩放的前后快照 |
| `%s BoardZoom ALIGNED: highView=%d bed=%d aspect=%.5f ...` | 棋盘左缘对齐完成 |
| `DEFER: ...` | 布局未就绪，推迟重试 |
| `watchdog: ...` | 视角状态看门狗（缩放被改回时自愈） |
| `View Angle set_state: ...` | 用户切换视角 |

### 3.6 组件补丁 `[CMP]`

前缀 `[CMP]` 只出现在组件补丁层，表示**字节级校验结果**：

```text
[CMP] glyph cache forced to 2048 (boot)
[CMP] glyph page limit -> 4 (boot)
[CMP] glyph cache: size=2048 pageLimit=4 pages=N cache=0x...
[CMP] almanac depress hook installed @+0x3c4c04
[CMP] dave idle-anim patch: already static @+0x1a7440
[CMP] conveyor count patch applied @+0x31585c
```

补丁写入前都会先核对原始指令字，不符则跳过并打印
`unexpected insn 0x...`。**看不到 `[CMP]` 行就说明补丁没生效**。

### 3.7 iOS 静态跳板（仅 iOS）

iOS 用打包期静态跳板代替运行时 hook，因此有一组专属日志：

| 关键字 | 含义 |
|---|---|
| `[STATIC] main image resolved via ...` | 定位到主程序镜像 |
| `[STATIC] scanning __TEXT for gate: ...` | 扫描 gate 区 |
| `[STATIC] gate_hdr=0x... stride=48 count=22` | gate 区定位成功 |
| `[STATIC] gate integrity check: all 22 sites OK` | 桩结构自检通过 |
| `[STATIC] gate site N: xxx mismatch 0x...` | 某个桩被覆盖（corrupted） |
| `[STATIC] no gate found; image head magic=...` | 找不到 gate |
| `[STATIC-ONLY] static sites used=N, no-site skipped=M` | 站点启用统计 |
| `[ERROR] hook(s) without static site` | 缺站点的功能会静默失效 |

### 3.8 诊断探针（仅 Debug 版 / 默认关闭）

以下前缀属于**诊断用途**，正式版默认不输出或频率极低，正常使用看不到：

| 前缀 | 用途 |
|---|---|
| `SHAKE*` / `CAMFRAME` / `PAN-END` | 相机震动与位移轨迹 |
| `A23A8C` / `C187C` / `AEF69C` | 坐标换算链路的字段快照 |
| `LRPKG` / `RSMDUMP` / `GRPDUMP` / `MMAPDUMP` | 数据包（RSB）结构转储 |
| `TBLSCAN` / `DUMP` / `RSB-OUTER` | 语言表与哈希表结构转储 |
| `CDN-INIT` / `APPLY` / `tblload` | CDN 清单与表加载的入参记录 |
| `[STAGE]` / `[COST]`（iOS） | 启动各阶段耗时打点 |
| `WORKTICK` / `DL4` / `DL5` / `FPSPROBE`（iOS） | 帧率与主循环采样 |
| `lowview-predict:`（Android） | 低视角预测，仅 Debug 编译保留 |

Android 侧这类行由 `LZT_DBG_LOG` / `LZT_DBG_ONLY` 宏控制，
`kDebugMode = false` 时**编译期即消失**（零开销）。
iOS 侧对应的是源码里一组 `static constexpr bool kEnable*Probe = false` 开关。

## 四、崩溃日志

崩溃时框架会尽量留下现场。

| | Android | iOS |
|---|---|---|
| 落盘位置 | 主日志文件（同文件追加） | 独立文件 `lztsettingsframework_crash.log` |
| 写入方式 | `dup` 出来的 fd + `write` | `open(O_APPEND)` + `write` |
| 内容 | 信号、故障地址、当前阶段、基址 | 信号、故障地址、当前阶段、基址、**寄存器 + 调用栈** |

```text
NATIVE_CRASH signal=11 fault=0x... stage=... base=0x...
NATIVE_CRASH_PC pc=0x...(+0x...) lr=0x...(+0x...) fp=0x... sp=0x... bt: +0x... +0x...
```

> **为什么要绕过 stdio**：崩溃可能发生在其他线程持有日志文件锁的时刻，
> 此时在 handler 里用 `fprintf` 写同一个 `FILE*` 会永久死锁，
> 崩溃记录整行丢失（Android 视角 Tab 崩溃时实测）。因此两端都改用
> 裸 fd 写入。Android 还额外挂了备用信号栈，保证栈溢出类崩溃也能留记录。

iOS 的崩溃日志是**追加**的，不受「每次启动清空」影响，可以保留多次崩溃现场。

## 五、怎么读

### Android

```bash
# 实时看
adb logcat -s settingsframework

# 取文件（连归档一起取）
adb pull /sdcard/Android/data/<包名>/files .
```

### iOS

- **越狱直装（企业签名）**：日志在游戏数据容器的 `Documents` 目录下。
- **LiveContainer**：日志在**内层 app** 的 `Documents` 目录，路径比直装多
  一层容器目录（形如 `Documents/Data/Application/<内层UUID>/Documents/`）。

也可以直接在设备上跑游戏二进制复现并抓日志：

```sh
A=/var/containers/Bundle/Application/<UUID>/PvZ2.app
cd /tmp && nohup "$A/PvZ2" > /tmp/run.out 2>&1 &
```

## 六、排查对照表

| 现象 | 先看（Android） | 先看（iOS） |
|---|---|---|
| 完全没有日志 | 是否执行了 `System.loadLibrary`；`lib/<abi>/` 里是否放了对应 `.so` | dylib 是否真的在 `.app/Frameworks/` 里；主程序是否有 `LC_LOAD_DYLIB` |
| 有基址但功能没反应 | 当前游戏版本的地址是否与 `offsets.h` 一致 | 同左，且看 `gate_hdr` 是否为 0 |
| 设置页一进去就崩 | 设置页相关地址与字段偏移是否来自同一游戏版本 | 同左，另看 `[ERROR] hook(s) without static site` |
| 没有语言 Tab | 是否配置了语言表来源；启用语言是否多于一种 | 同左，另看 `LangTable: source=` 是否有输出 |
| 切换语言后文本没变 | 语言热重载与本地化刷新均为 arm64 实现 | 看走的是规则①/②/③ 哪一条；`LawnStrings: loaded N entries` 是否出现 |
| 语言表为空 | `LangTable:` 来源行 | No_Backup 重定向是否成功（LiveContainer 下可能失败） |
| 缺少字形 / 缺字 | `[CMP]` 行 | `[CMP]` 行 |
| 启动卡在加载图标 | —— | 确认 dylib 是**静态模式**构建（`LZT_STATIC_ONLY=1`） |
| 反复重启 / 补丁被重装 | `REHOOK` / `REINSTALL` 行 | —— |
| 主线程卡顿 | —— | `[HB] main thread STALLED` |

## 七、反馈问题时请提供

- 游戏版本、宿主环境（直装 / LiveContainer）、设备与系统版本
- Android 附包名与 CPU 架构，iOS 附宿主类型
- 复现步骤（在哪一步、做了什么操作）
- 出问题**前后**的日志片段（各留几十行即可）
- 构建模式（Release / Debug）

日志里可能含包名与内存地址，公开前请自行脱敏。
